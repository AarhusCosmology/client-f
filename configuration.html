Configuration and defaults#

The complete field inventory is regenerated from config/config.py and profiles/config.py during every documentation build. It records field types and omitted-field defaults, using explicit YAML parser fallbacks when they differ from constructor defaults. It does not import TensorFlow or a likelihood backend.

Defaults and recommended settings#

Most new methods are opt-in, so a run that takes only the defaults is not the method of the real runs. input/recommended_near_gaussian.yaml and input/recommended_non_gaussian.yaml are complete configurations with those settings; the boost guide says which to take.

Read absence, null and an empty mapping differently#

  • An absent acquisition.audit disables the audit, and so does audit: false. audit: {} activates default audit settings, as do audit: true and, in this parser, audit: null (converted to an empty mapping). The same holds for the top-level derived section.

  • An absent acquisition.boost disables boosting, and so does boost: false. boost: {}, boost: true and boost: null do not form a valid boost: n and start_iteration are required.

  • An absent derived section disables emulator training. Use an explicit mapping to configure it.

  • Types are not a substitute for validation: e.g. boost walkers must be even and at least four, steps at least 100, region greater than one, and mixing strictly between zero and one.

Interpretation

training.warm_start

true

Transfer the preceding network’s weights, with the raw predictions kept when the scalers change; false starts each network from random weights. A network warm-started after the boosts began keeps the weights at the end of its schedule; the ordinary loop and trainings from random weights keep the epoch with the lowest validation loss

training.random_start_weights

best

A training of the boost phase from random weights (warm_start: false, the first training after the background is fitted, the members from random weights) keeps the epoch with the lowest validation loss; last keeps the weights at the end of its schedule, as a warm-started one does (guide)

training.members

1

One training per network. K trains each network of the boost phase K times (rank 0 warm-started, the others from random weights on otherwise idle ranks; the tempered phase trains once; it needs acquisition.boost) and keeps one, chosen on held-out newest points or, with training.member_pilot, by true evaluations at each member’s own posterior points, each member judged without its constant offset (training.member_pilot_score: corrected; rms keeps it); training.member_device: auto trains them on a GPU where their process sees one (guide)

Inputs and compatibility#

The training YAML and profile YAML are different schemas. Put a setting in the command’s own configuration; the profile CLI can print resolved settings with --dry-run. Both reject settings they do not know, and the run stops before its initial design when a loss, an activation or the number of walkers does not fit the problem.

Resume preserves the settings required to reproduce an existing study. A default does not authorise changing the method or domain of a saved profile study. See migration notes and profile resume rules.

Limits and conditional settings#

Detailed allowed values and interactions are maintained beside their workflows:

  • Audit budgets and failure handling

  • Boost settings and density selection

The generated inventory lists every schema field; it is not a claim that every positive value or every combination is supported. The parser and workflow validation remain authoritative.

Conditional convergence and phase limits#

For metric: tempered_batch_scatter, omitting threshold gives 1.2; for gaussian_posterior_drift, threshold is required. The generated table marks this condition explicitly. consecutive must be at least one, and tempered_batch_scatter requires a positive threshold. Its units are multiples of sampling.temperature, not absolute native log probability.

acquisition.boost.boosts limits scheduled boost-phase iterations when no explicit -i is supplied. A no-mode fallback still consumes a phase iteration. It does not promise a fixed number of successful posterior batches. The effective end is also limited by the run’s iteration ceiling. A saved early start in boost/start.json is respected on continuation. See handover semantics.

The profile region setting differs from boost region: run inherits a saved region, null disables it, and a positive number overrides the edge. If the selected network has no saved region, the bare network is used. See region-aware profiles.
